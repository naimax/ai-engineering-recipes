# Нотация: несколько проходов и гейт между ними

Связанная практика: [контроль правил агента на Хабре](https://habr.com/ru/articles/1074764/) задаёт, что удерживать
в одном проходе. Здесь дописываем, когда проходов несколько: кто ставит вердикт,
где между ними живёт факт, у кого какая зона записи.

Класс поломки: параллельная работа без общего факта; проход сам себе ставит «принято».

## Инварианты и зоны записи

Три инварианта, без которых цепочка хуже одного чата:

| Инвариант | Формулировка для вашего файла правил | Признак нарушения |
|---|---|---|
| Вердикт | «Принято» действительно только при существующем файле ревью от другого прохода. Нет файла: статус откатывается | автор правит шапку своего документа на «готово» |
| Факт | Следующий проход открывает файл сам; в промпт идут 3–7 путей, а не пересказ и не дамп чата | решение стадии живёт только в переписке |
| Зона | У каждого файла один хозяин. Параллель только без общих файлов | два прохода правят один файл |

Таблица зон (заполнить под себя):

| Роль | Читает | Пишет | Не трогает никогда |
|---|---|---|---|
| оркестратор | всё по путям задачи | журнал прогонов | продукт, файлы вердиктов |
| исполнитель | входные пути | свою рабочую зону | файлы вердиктов |
| судья | артефакт исполнителя | только свой файл вердикта | проверяемые файлы |
| ортогональный судья | сам артефакт, без чек-листа | свой короткий вердикт | всё остальное |

Ловушка прав: соблазн запретить судье запись целиком велик и выглядит безопасно.
Так делать нельзя, если судья обязан оставить файл ревью: раз роль не может писать,
её файл напишет вызывающий, то есть автор работы, и вы получите самоаппрув.
Полный запрет записи только для судьи, который отдаёт вердикт репликой и ничего не оставляет.

## Форматы передачи и вердикта

Передача между проходами:

```markdown
Задача: <одна фраза, что должно существовать после прохода>
Читать (3–7 путей):
- <путь>: <зачем>
Писать: <одна зона>
Готово, когда: <проверяемое условие>
```

Инструкция сверху, условие приёмки снизу: середина длинного промпта читается хуже краёв.
Текст длиннее полусотни строк передаётся путём, а не вставкой.

Вердикт:

```markdown
verdict: PASS | FAIL
проверял: <пути, которые открыл>
не сошлось:
- <пункт>: <что именно и где>
```

Первая строка машиночитаемая: по ней оркестратор ветвится. «В целом хорошо» не вердикт.
Нечем проверить: FAIL с указанием, чего не хватает.

## Синтаксис в трёх инструментах

| Что задаём | Cursor | Claude Code | Codex |
|---|---|---|---|
| где лежит роль | `.cursor/agents/<name>.md` | `.claude/agents/<name>.md` | `.codex/agents/<name>.toml` |
| формат | markdown + frontmatter | markdown + frontmatter | TOML |
| роль | тело файла | тело файла | `developer_instructions` |
| права | `readonly` | `tools` / `disallowedTools` | `sandbox_mode`, `mcp_servers` |
| модель | `model` | `model` | `model` |
| когда звать | `description` | `description` | `description` |

Переезд между инструментами меняет формат файла, а не устройство контура.

## Проверка контура

Судью не зовут ни разу: во всех трёх инструментах делегирование выбирается по тексту
описания. Слабое описание: судья не вызовется, и это не видно, работа просто идёт без
вердикта. Описание пишется как условие вызова («проверка завершённой работы перед тем,
как считать задачу закрытой»), а не как титул роли («ревьюер кода»).

Нотация заполнена, когда:

1. В чистом чате видно, что судья существует и его описание совпадает с моментом вызова.
2. На одной задаче в переписке два разных обращения, а не одно «сделай и проверь».
3. Заведомо сломанный вход даёт FAIL, заведомо чистый PASS. Одинаковый вердикт на обоих
   означает, что сломан судья, а не исполнитель.
